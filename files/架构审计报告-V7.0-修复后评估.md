## 1. 模块解耦与开闭原则 (Decoupling & OCP)

**评级：B（修复前 C）**

### 1.1 路由硬编码 → 已修复 ✅

`entry.py:108-109`：
```python
from skills.agent.registry import get_fast_handlers
_FAST_HANDLERS = get_fast_handlers()
```

不再硬编码，从 `TOOL_REGISTRY` 中带 `"fast_path": True` 标记自动派生。新增快速工具仅需在注册表中加一行。OCP 合规。

### 1.2 `_apply_param_map` 特例分支 → 已简化 ✅

scope 映射（`today→今天任务`）已下沉到 `task_query.py` 内部，`registry.py:184-203` 中仅剩三个分支：`None→ctx`、`"params"→全参`、`else→get`。

**仍存问题 🔶**：`else` 分支存在多层回退链：
```python
args.append(params.get(source_key, params.get("user_input", params.get(source_key, ""))))
```
如果 LLM 未传 `name` 但传了 `user_input`，会静默用 `user_input` 填充而非报错——这掩盖了 LLM 的参数构造错误。

### 1.3 Workflow 定义 → 已清理 ✅

`workflow/definitions.py` 中 `task_query`、`knowledge_retrieve`、`profile_query` 三个 dead workflow 已删除。

**新发现：`list_triggers()`** 是 dead code，定义后无人调用。

## 2. 数据流与状态管理 (Data Flow & State Management)

**评级：A−（修复前 B）**

### 2.1 UserContext 强类型 → 已修复 ✅

```python
@dataclass
class UserContext:
    name: str = ""
    role: str = ""
    team: str = ""
```

`RequestContext.user` 类型改为 `Optional[UserContext]`。`resolve_user()` 返回 `UserContext`。六处 `.get("name")` → `.name` 已全部更新。

**仍存问题 🔶**：`event`、`subject_context`、`result` 字段仍是 `Optional[dict]`——裸字典无 schema 约束。当前不影响行为，但属于薄弱环节。

### 2.2 多命令 ctx 隔离 → 已修复 ✅

`engine.py:178`：
```python
loop_ctx = dataclasses.replace(ctx) if is_multi else ctx
```

**⚠️ 注意**：`dataclasses.replace()` 是**浅拷贝**。`RequestContext` 中的 `event`、`subject_context` 等 `dict` 字段在 `loop_ctx` 中与原 `ctx` 共享引用。若某个 handler 修改了 `ctx.event['key']`，其他循环迭代可见此改动。当前这些字段在 multi-command 场景下不会被 handler 修改，故非阻塞性问题，但属潜在风险。

### 2.3 参数端到端类型

工具参数是裸 dict 流经全程：
```
LLM JSON → _parse_decisions → execute → _apply_param_map → handler
```
无 `ToolParams` 类型约束。`validate_params()` 只检查必填键存在，不校验值类型或 enum 范围。

## 4. 容错、短路与降级机制 (Fault Tolerance & Resilience)

**评级：B+（持平）**

### 4.1 Fallback 链完整 ✅

```
LLM 调用失败 → _call_llm 返回 None → _fallback_search → knowledge_retrieve → "已记录：..."
JSON 解析失败 → _call_llm 返回 None → 同上
工具未知(单命令) → _fallback_search
工具未知(多命令) → 标记错误继续
参数校验失败(单命令) → 返回提示
参数校验失败(多命令) → 标记错误继续
执行异常 → try/except → [Cipher:error]
```

无覆盖空白。多命令模式下各子命令失败不阻塞其他命令。

### 4.2 重试机制

单命令执行异常时有 LLM 重试（`engine.py:203-223`）。**多命令模式无重试**——直接跳错误。属于设计取舍而非缺陷（多命令场景重试延迟会累积）。

### 4.3 Fast-Path / Complex-Path 分流 ✅

`entry.py:159-181`：
- correction + 高置信 → WorkflowEngine
- 非 event + 高置信 → `_fast_dispatch`（绕过 LLM）
- 其余 → Agent/LLM 路径

阈值 `CT.HIGH = 0.7`。**注意**：`CT.EXECUTE = 0.6` 仅在测试中使用（`test_confidence.py:38`），生产代码中不被引用。

### 4.4 无显式短路机制 ❌

无 `is_aborted` 或 `cancel_token`。若某 handler 陷入长时间运行（如 `reminder_set` 的网络调用），无法外部切断。`llm_client` 有 120s timeout，但无断路器模式。

## 5. LLM/Agent 专项架构审计 (Agentic Specifics)

**评级：B+（修复前 B）**

### 5.1 Token 控制

`AGENT_SYSTEM_PROMPT` 使用 `brief=True` 模式（`engine.py:140`），工具列表仅包含 id + description，无 params schema 展开。实测 token 量：
- 单命令 prompt：~520 tok → 降为 ~420 tok（预估）
- 多命令 prompt：~536 tok → 降为 ~436 tok（预估）
- `max_tokens=800` 不变

**影响**：参数字段不发给 LLM，LLM 需自行推断参数结构。这降低了 prompt 长度但可能降低参数提取精度。

### 5.2 Schema enum 元数据 ✅

`task_query.scope` 已添加 `"enum": ["today", "tomorrow", "week", "month"]`。

**仍存问题 🔶**：`validate_params()` 不校验 enum 值——enum 字段仅作文档用途，无程序化执行。

### 5.3 异步解耦

异步操作均通过 `threading.Thread(daemon=True)` 实现：
- `reflector.reflect()` ✓
- `ProactiveDaemon.start_loop()` ✓

无 `asyncio`/`async` 使用。`_async_llm_score` 方法名含 "async" 但实际是同步调用（`memory_core.py:375`）。

## 结论

10 步修复将系统从 **6 维度评分 2.0/5.0** 提升至 **3.3/5.0**。维度 1（OCP）和维度 2（数据流）改善最显著。维度 4（容错）和维度 6（可测性）仍有结构性缺口，需下一轮处理。

如进入第二轮修复，建议按此优先级：
1. 修 macOS 硬编码（阻塞 Linux 部署）
2. 新增 `event`/`subject_context` schema 类型
3. `_apply_param_map` 回退链精简
4. `_execute_loop` 拆分 retry 逻辑
5. 补齐 registry/engine 核心逻辑的单元测试
