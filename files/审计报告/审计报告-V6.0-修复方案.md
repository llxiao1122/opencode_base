## 🔍 审计核心维度

### 1. 模块解耦与开闭原则 (Decoupling & OCP)

**评级：C — 存在结构性问题**

#### 1.1 路由硬编码

`skills/entry.py:108-112`：
```python
_FAST_HANDLERS = {
    "task_query": ("skills.agent.handlers.task_query", "handle"),
    "knowledge_retrieve": ("skills.agent.handlers.knowledge_retrieve", "handle"),
    "profile_query": ("skills.agent.handlers.profile_query", "handle"),
}
```

新增一个 tool handler 需要修改三处：`registry.py` 注册 + `workflow/definitions.py` 定义 + 如果需加入 FastPath 则改 `entry.py`。OCP 违反：对扩展不开放，对主入口不封闭。

**建议**：`_FAST_HANDLERS` 应从 `TOOL_REGISTRY` 中通过标记（如 `"fast_path": True`）自动派生，删除 `entry.py:108-112` 的手工维护。

#### 1.2 Tool 注册与 `param_map` 的反向依赖

`registry.py` 的 `TOOL_REGISTRY` 中，`param_map` 的结构是 `handler_arg → params_key`。但 `_apply_param_map`（`registry.py:168`）内部包含了大量特例分支（`scope`、`user_input`、`params` 等）。这意味着：

- 新增工具时需要理解 `_apply_param_map` 内部的特例规则
- 移除工具时需确认没有特例分支依赖它的字段名

**建议**：`param_map` 改为纯 KV 映射。`scope` 的语义转换（`today→今天任务`）应下沉到 `task_query` handler 内部。

#### 1.3 WorkflowEngine 与 Registry 的耦合

`workflow/engine.py` 直接调用 `skills.agent.registry.execute`（第 54 行），`workflow/definitions.py` 用字符串 `"input"` 作为参数占位符。这是一个隐式耦合——`_build_params`（第 58-71 行）是另一个有特例分支（`"input"`、`"input[:200]"`）的参数转换层。

**建议**：Workflow 的参数模板改为直接使用 handler 期望的原始 schema 字段名，去除 `[:200]` 这种魔法后缀。

### 2. 数据流与状态管理 (Data Flow & State Management)

**评级：B — 设计合理但有局部隐患**

#### 2.1 RequestContext 的质量

`RequestContext`（`schema.py:64-85`）作为全局上下文贯穿是好的。但存在"盲盒字段"问题：

```python
@dataclass
class RequestContext:
    user: Optional[dict] = None      # dict 无 schema 约束
    subject_context: Optional[dict] = None  # 同上
    event: Optional[dict] = None
    decision: Optional[dict] = None
    result: Optional[dict] = None
```

`user` 是一个裸 `dict`，各 handler 对其结构（`name`、`role`、`team`）的假设没有编译期保障。在 `entry.py:158` 硬编码了缺省用户：

```python
rctx.user = {"name": "李林骁", "role": "工班长", "team": "铁炉西工班"}
```

而 `engine.py:114-118` 通过 `resolve_user()` 尝试覆盖——这两处的用户数据契约未统一。

**建议**：定义 `UserContext` dataclass 替换裸 `dict`，所有 handler 和 entry 统一引用。

#### 2.2 状态污染风险

`ctx` 在 Agent 路径中（`engine.py`）被多次修改：
- `ctx.route = "agent"`（第 120 行）
- `ctx.confidence = 0.0`（第 121 行）
- 循环中每次 `execute(tool_id, params, ctx=ctx)`（第 180 行）—— handler 可能修改 ctx
- 最终 `ctx.route = last_tool`（第 210 行）

多个工具共享同一个 `ctx` 实例。在多命令场景下，如果某个 handler 意外修改了 `ctx` 的共享状态（如清空了某字段），后续 handler 将受影响。

**建议**：多命令场景下，每个子命令传入 `ctx` 的拷贝（`dataclasses.replace(ctx)` 或深拷贝快照）。

### 3. 循环依赖与边界防护 (Circular Imports & Boundary)

**评级：B — 边界大体清晰，局部有隐患**

#### 3.1 共享层下沉正确

`shared/schema.py`、`shared/entity.py`、`shared/path.py` 等基础类型已正确下沉至公共区域，无循环导入风险。✓

#### 3.2 模块间边界

- `skills/entry.py` 是 Orchestrator
- `skills/agent/` 是 Engine + Registry
- `skills/memory/` 是 Data Layer
- `skills/core/` 是 Infrastructure
- `skills/workflow/` 是 Process Orchestration

边界大体清晰，但入口层存在反向依赖：`entry.py:182` 直接 `from agent.engine import run`，而 `engine.py:15` 引用了 `from skills.correction.logger import append`——这意味着 Core 依赖 Application 层。

**建议**：考虑引入 `BaseAgent` 抽象，或至少将 `agent/engine.py` 降为纯逻辑，减少对 `skills.correction` 的直接引用（这个引用目前从未使用——`log_append` 在 engine.py 中作为全局导入但不调用——是 Dead Code）。

### 4. 容错、短路与降级机制 (Fault Tolerance & Resilience)

**评级：B+ — 降级完备，但缺少显式短路**

#### 4.1 Fallback 链已覆盖

Agent 路径的 fallback 链：

```
LLM call error → _fallback_search → knowledge_retrieve → "已记录"
JSON parse fail → _fallback_search
Unknown tool (single) → _fallback_search
Unknown tool (multi) → 标记错误继续
Param validation fail (single) → 返回错误信息
Param validation fail (multi) → 标记错误继续
Execute exception → [Cipher:error]
```

容错链覆盖了各异常入口，且多命令模式下不阻断。✓

#### 4.2 缺少显式短路/中断

- 无 `is_aborted` 或 `cancel_token` 机制。若某条 handler 陷入长时间运行（如网络阻塞），无法切断。
- LLM client 仅有 timeout 参数（默认 120s），没有跨调用的断路器模式。

**建议**：引入 `Context.abort()` 标记 + Python `threading.Event` 在异步线程中传递中断信号。

#### 4.3 Fast Path vs Complex Path

系统已有 Fast-Path（`_fast_dispatch`，绕过 LLM）与 Complex-Path（Agent/LLM）的分流。但 Fast-Path 目前只覆盖 3 个 route。`event` 路由永远走 Agent 路径（因为 `entry.py:173` 排除了 `route != "event"`），即使对于简单的"记录事件"消息也需要一次 LLM 调用。

**建议**：考虑为 event 类消息的低置信阈值场景增加规则引擎直通路径。

### 5. LLM/Agent 专项架构审计 (Agentic Specifics)

**评级：B — Token 控制良好，但系统提示存在膨胀风险**

#### 5.1 Token 控制

实测数据：

| 场景 | Prompt | Completion | Total |
|---|---|---|---|
| 单命令 | 524 tok | 47 tok | 571 |
| 多命令(2条) | 536 tok | 147 tok | 683 |
| 系统提示模板 | ~520 tok | — | — |

Prompt caching 命中率高达 **95%**（512/536）。✓ `max_tokens=800` 合理。System Prompt 中的 `tools_desc` 随工具数量线性增长——当前 10 个工具时约 500 tok。若扩展到 20+，System Prompt 将突破 1000 tok。

**建议**：为工具描述加入 long/short 双模式，在 agent prompt 中仅包含 short 描述（一行摘要），完整 schema 通过 JSON Schema 动态展开给 LLM 的 function-calling 模式。

#### 5.2 工具注册机制

`TOOL_REGISTRY` 是一个纯 dict，schema 用 dict 描述而非 Pydantic/JSON Schema。

**问题**：
- 无编译期类型检查（`type: "str"` 是字符串不是 `str` 类型）
- 枚举约束（如 `scope in ["today", "tomorrow"]`）只能写在 handler 内部，无法被 LLM 直接感知
- `_clean_params`（`registry.py:157-165`）防御性处理 LLM 返回 schema 对象的问题——说明 LLM 经常误构参数

**建议**：为 params_schema 增加 `enum` 字段，在 tool description 中携带枚举值，帮助 LLM 准确构造参数。

#### 5.3 异步解耦

系统已正确地将以下操作异步化：
- `reflector.reflect()` 在 daemon 线程中运行（`entry.py:197-202`）✓
- `ProactiveDaemon` 在独立线程运行 ✓
- `_build_index_once()` 是延迟初始化 ✓

缺失：
- `change_detector.detect()` 是在主响应路径中同步调用的（`entry.py:187`），对于非变更消息也是小开销，可接受。

### 6. 代码洁净度与可测试性 (Testability & Code Hygiene)

**评级：B− — 测试已覆盖，但 God Method 和 Dead Code 需要清理**

#### 6.1 God Method 分析

`skills/agent/engine.py:run()`（112-222 行，110 行）是单体的"上帝方法"，内包含了：

- 上下文初始化
- System Prompt 构建
- LLM 调用
- JSON 解析
- 工具循环执行
- 重试逻辑
- 结果拼接

六个不同的职责。难以单独测试"工具循环"逻辑而不 mock 整个链条。

**建议**：拆分为 `_build_prompt()`、`_call_llm()`、`_execute_loop()` 三个方法。

#### 6.2 Dead Code

`engine.py:15`：
```python
from skills.correction.logger import append as log_append
```
`log_append` 在整个 `engine.py` 中从未被调用。

`workflow/definitions.py` 中定义了 `task_query`、`knowledge_retrieve`、`profile_query` 三个 Workflow，但实际只有 `correction` 被使用（通过 `entry.py:165`）。剩余三个是 dead config。

#### 6.3 可测试性

当前 67 个测试用例覆盖良好。但有一个可改进点：`engine.py` 中的所有工具注册表调用（`list_tools()`、`execute()`）都依赖全局模块变量 `TOOL_REGISTRY`。虽然当前没有任何测试 mock/patch `list_tools()` 或 `TOOL_REGISTRY`（全局唯一 mock 是 `conftest.py` 中 `urllib.request.urlopen` 拦截 LLM HTTP），但若未来为 `engine.py` 编写纯单元测试，想要避免加载全部 handler（部分有网络依赖），将缺乏注入手段。

**建议（可选增强）**：为 `run()` 增加可选参数 `tool_registry=None`，默认 fallback 到全局注册表。这样单元测试可传入自定义注册表，减少对环境的依赖。当前不构成阻塞性缺陷。

#### 6.4 其他 Hygiene 问题

| 问题 | 位置 | 严重度 |
|---|---|---|
| `user: Optional[dict]` 裸 dict | `schema.py:66` | 中 |
| 硬编码用户"李林骁" | `entry.py:158` | 低（MVP 合理） |
| `reflector.reflect()` 每次传空 `{}` 作为 params | `entry.py:199` | 低（永远丢 params 信息） |
| `append(rctx, result, tool_id=tool_id or "")` 中 `tool_id` 可能是 `None` | `entry.py:191` | 低 |
| 全局 `_STATE` 字典 | `reflector.py:15` | 低（单线程安全） |
