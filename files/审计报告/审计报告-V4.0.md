## 1. 架构总评与健康度评分

**评分：6.5 / 10**

| 维度 | 分数 | 一句话 |
|------|------|--------|
| 模块解耦 | 5 | fast path 干净，Agent path 耦合重 |
| 数据流 | 6 | RequestContext 已定义但形同虚设 |
| 边界 | 8 | 无循环依赖，shared/ 下沉到位 |
| 容错 | 5 | 吞异常式抗毁，无短路无熔断 |
| Agent 架构 | 5 | 1 次 LLM 调用太浅，prompt 内嵌 schema |
| 可测试性 | 7 | 60 tests 覆盖核心路径，但 God Class 难测 |

**优点**：FAISS 直通快路径（task/knowledge/profile）干净利落；`shared/schema.py` 数据合约下沉到位，无循环依赖；容错链从未崩溃——但代价是所有异常被 `except: pass` 吞掉。

**缺点**：Agent 路径（engine → registry → handler）耦合在 `sys.path` hack、隐式 dict 传参、RequestContext 定义后几乎没被用的状态中。Agent 只做 1 轮 LLM 调用，多步推理、反思、记忆增强全部缺失。两个 God Class（MemoryCore 722 行，observation_store 450 行）把逻辑和持久化揉在一起。

## 2. 🔴 红线隐患

### R1. `except: pass` 遍布全系统——静默吞噬所有错误

**定位**：entry.py:36/41/55/95/150，engine.py:69/73/109/132，registry.py:135，logger.py:49，observation_store.py，memory_core.py...

**危害**：生产环境出现任何异常（文件权限、JSON 解析、网络超时）全部静默消失。调试时要靠猜，没有堆栈、没有告警。`_build_index_once` 里 FAISS 构建失败 → 后续 classify() 永久返回 0.0 → 全量流量进 Agent → Agent 失败 → `_fallback_search` → 用户看到 "[Cipher]\n已记录：xxx" 但没人知道为什么。

```python
# entry.py:36 — 索引构建失败你永远不知道
try:
    from routing.builder import build
    build()
except Exception:
    pass
```

### R2. `sys.path` 硬编码——进口路径取决于入口文件位置

**定位**：entry.py:16-17，engine.py:16，registry.py:10，observation_store.py:10，memory_core.py:53...

**危害**：每个文件独立 resolve ROOT 并 `sys.path.insert(0, ...)`——从 tests/ 导入 vs 从 skills/ 导入，路径顺序不同。`conftest.py` 也在做同样的事。这导致：
- 从 `/skills/routing/` 启动 vs `/` 启动 vs `tests/` 启动，`import` 可能命中的是旧缓存
- 某些模块在不同入口下 import 行为不同

### R3. Agent Engine 单点故障——所有低置信流量经过同一个 LLM 调用

**定位**：engine.py:108 — 唯一的 LLM 调用点

**危害**：
- LLM 超时/限流 → 整站不可用（所有低置信/event 流量）
- 返回非 JSON → fallback 到 `_fallback_search`，没有重试
- 当前 Zhipu API 免费但有 5 RPM 限制——超过即 429，3 次重试后返回 error dict，然后被 engine.py:109 检测到走 fallback
- fallback 链末端（engine.py:74）直接返回 `[Cipher]\n已记录：{query}`，用户无法区分"已记录"和"请求失败"

## 3. 🟡 架构债务与改进建议

### Y1. RequestContext 定义良好但未贯通——用 dict 替代了类型契约

**定位**：`shared/schema.py:47-66` vs 实际 handler 签名

RequestContext 定义了 `message/user/channel/request_id/status/error/route/confidence/event/decision/result/reply` 等字段。实际上：
- fast dispatch 虽然传了 `rctx` 但 handler 并不填充 `ctx.result`
- `registry.py:execute()` 创建了全新的 `_default_ctx()` 而不是复用入口传来的
- `logger.py:append()` 读 `ctx.confidence`——但在 Agent path 中这个值在 `engine.py:129` 才被覆写为 0.8
- 没有统一的 request_id 链路追踪

**建议**：让 RequestContext 成为唯一贯穿对象，所有 handler 签名统一为 `handle(params, ctx)`，handler 填充 `ctx.result`。registry.execute() 接受传入 ctx 而非创建新的。

### Y2. `registry.py:execute()` 暗含两套参数映射逻辑

**定位**：registry.py:12-26 (`_TOOL_PARAM_MAP`) + :163-192（if/elif 链）

这是最严重的代码异味。`_TOOL_PARAM_MAP` 用声明式映射了一部分工具的参数，但 `notification_push`、`event_record`、`task_create`、`task_feedback`、`org_lookup` 又走到了下面硬编码 if/elif 链。

两套路径做同一件事（将 LLM 返回的 `params` dict 转为 handler 的位置参数）。新增工具时必须同时在两个地方加代码。

**建议**：统一用声明式参数映射（`_TOOL_PARAM_MAP` 模式），消除 if/elif 链。或让 handler 统一接受 `(params, ctx)` 签名，由 handler 自己解包。

### Y3. God Class: MemoryCore（722 行）和 observation_store（450 行）

**定位**：`memory/memory_core.py`, `memory/observation_store.py`

MemoryCore 承担了：embedding 加载、FAISS 索引管理、markdown chunking、Knowledge 读取/写入/搜索、事件记忆（episodic）写入/检索、记忆冲突检测、重要性评估、聚类压缩、反射循环、LLM 调用。这是典型的"上帝对象"——修改任何功能都需要理解全部 722 行。

observation_store 同样混合了：索引读写、实体名缓存（全局 mutable 状态 `_entity_names`）、FAISS 增量更新、LLM 分类、去重、观察记录写入。

**建议**：按职责拆分为 `core/embedder.py` / `core/indexer.py` / `core/chunker.py` / `core/knowledge.py`。

### Y4. 全局可变状态导致测试间干扰

**定位**：observation_store.py:18 `_entity_names = None`、:15-16 全局锁、logger.py:17 `_session` + `_seq`、entry.py:23 `_index_built`

- `_entity_names` 是模块级缓存，写入后不清除——测试 B 可能读到测试 A 写的数据
- `logger._session` 和 `_seq` 跨测试持续增长
- `conftest.py` 通过 `patch` 和 `OP_SKIP_BG=1` 来补救，但这掩盖了真实依赖关系

**建议**：模块级缓存加 reset 函数，测试 fixture 中显式重置。

### Y5. LLM Client 不支持 streaming、无请求级 timeout 传播

**定位**：`core/llm_client.py`

`call()` 是同步阻塞的，不支持流式返回。所有请求用同一个 timeout 参数（默认 120s），没有 per-request 控制。

另外，`_resolve_config()` 每次调用都重新读取 opencode.jsonc 并执行复杂的配置解析——可以用 `lru_cache` 或启动时一次加载。

### Y6. `route_seeds.json` 和 `entity_index.json` 的写入竞争

`learner.py` 会写入 `route_seeds.json`（添加修正种子），`change_detector.py` 写入 `entity_index.json`。这两个文件都可能被 `_build_index_once()` 和 `classify()` 同时读取，但没有任何文件锁。写入是 `atomic_write`（tmp+replace）形式，读取端在高并发时可能读到不完整状态。

### 4.2 Priority Fix: Registry 参数映射统一

**Before**（两套映射并存）:
```python
_TOOL_PARAM_MAP = {
    "task_query": {
        "msg": lambda p, ctx: ...,
        "ctx": lambda p, ctx: ctx,
    },
    ...
}

def execute(tool_id, params):
    ...
    if tool_id in _TOOL_PARAM_MAP:
        ...
    elif tool_id == "notification_push":
        result = handler(params.get("title"), params.get("content"))
    elif tool_id == "event_record":
        result = handler(params)
    ...
```

**After**（统一为签名映射）:
```python
TOOL_PARAM_MAP = {
    "task_query":         {"handler": "handlers.task_query:handle",     "params": ["msg", "ctx"]},
    "knowledge_retrieve": {"handler": "handlers.knowledge:handle",     "params": ["topic", "ctx"]},
    "profile_query":      {"handler": "handlers.profile:handle",       "params": ["name"]},
    "notification_push":  {"handler": "handlers.notification:handle",  "params": ["title", "content"]},
    "event_record":       {"handler": "handlers.event_record:handle",  "params": ["params"]},
    "task_create":        {"handler": "handlers.task_create:handle",   "params": ["summary", "deadline", "assignee"]},
    "task_feedback":      {"handler": "handlers.task_feedback:handle", "params": ["action", "executor", "task_id"]},
    "org_lookup":         {"handler": "handlers.org_lookup:handle",    "params": ["name"]},
}
```

`params` 数组定义了从 `clean_params(params)` 中提取哪些 key 以及顺序，`execute()` 循环映射 + 传参，消除所有硬编码 if/elif。

## 5. 🚀 未来扩展建议

### 5.1 异步 Agent 反思（Phase 4 预热）

当前 Agent 路径是同步 1 次 LLM 调用。要支持多步推理：

```
entry → classify → Agent.run()
                    ├── call LLM → 决策
                    ├── execute tool
                    ├── call LLM → 反思（异步，不阻塞回复）
                    └── 返回用户
```

预留点：`engine.py` 的 `run()` 应当返回 `(reply, background_tasks)`，其中 `background_tasks` 是 post-response 的协程列表。

### 5.2 分布式部署预留

当前 MemoryCore 是本地 FAISS 索引（`state/` 下 .index 文件）。如果后续需要多实例：
- FAISS 索引需改为向量数据库（Milvus/Qdrant）或内存广播
- `state/tasks.json` 需改为 SQLite/PostgreSQL
- LLM client 需支持请求级的 `trace_id` 传播

### 5.3 工具发现机制动态化

当前 `TOOL_REGISTRY` 是 registry.py 里的静态 dict。扩展方案有两种：

**(A)** Handler 自注册（推荐）：
```python
from agent.registry import register

@register(
    id="task_query",
    description="查询工作安排",
    params={"scope": {"type": "str", "required": False}}
)
def handle(msg: str, ctx: RequestContext) -> str:
    ...
```

**(B)** YAML/JSON schema 文件声明：
```yaml
# schemas/tools/task_query.yaml
id: task_query
handler: handlers.task_query:handle
params:
  scope:
    type: str
    required: false
    default: today
```

### 5.4 多维度监控预留

当前只有 `decision_log.jsonl` 一种日志。需要增加：
- 每个请求的耗时记录（FAISS classify + Agent LLM call + tool execute）
- 成功率/失败率统计（按 route、按 tool）
- LLM token 用量统计

这些可以在 `entry.py` 的 `handle_core()` 开始/结束时注入，加一个 `@timed` 装饰器或 context manager。

### 5.5 插件生态

当前插件只有 dingbot（`plugins/dingbot/`），硬编码为 `skills/plugins/` 下的子模块。正规化方案：

```python
# skills/plugins/__init__.py
_plugins = {}

def discover():
    for p in Path(__file__).parent.iterdir():
        if p.is_dir() and (p / "plugin.json").exists():
            spec = json.loads((p / "plugin.json").read_text())
            _plugins[spec["name"]] = spec
```

每个插件通过 `plugin.json` 声明自己的 hooks（`on_notification`, `on_event`, `on_llm_call` 等），Engine 在关键节点触发 hooks。
